# Xata OSS native PostgreSQL gateway assessment

Inspected upstream: [`xataio/xata` at `98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd`](https://github.com/xataio/xata/tree/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd), main commit dated 2026-09-24. The pinned [LICENSE](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/LICENSE) is Apache-2.0; no gateway-specific override was found. ## Reusable component boundaries

| Boundary | Observed upstream implementation | Integration implication |
| --- | --- | --- |
| Client protocol and TLS | [TLS initiator](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/initiator/initiator.go) requires TLS, handles PostgreSQL SSL negotiation and direct TLS, extracts SNI, and dispatches startup/cancellation packets. | Reusable protocol machinery; external DNS, certificate issuance/renewal and client compatibility remain installation responsibilities. |
| Routing | [BranchResolver](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/session/resolver.go) maps `(serverName, fallbackEndpoint)` to `{ID, Address}`. The built-in resolver constructs `branch-<id>-<endpoint>` Services in one shared namespace. | A PGCF adapter must resolve approved environment hostnames to the actual Services in separate `pgcf-*` namespaces. |
| Authentication and sessions | [Proxy](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/session/proxy.go) forwards the startup packet; [session](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/session/session.go) then copies connection bytes. PostgreSQL or PgBouncer performs native database-role authentication. | Keep PostgreSQL roles and credential rotation separate from management API tokens. Forwarding alone does not establish authorization or invalidation guarantees. |
| Pooling | The resolver distinguishes direct `rw`/`ro`/`r` and `pooler` endpoints. The native proxy does not implement a second transaction pooler. | Compatible with CNPG owning PgBouncer; advertise a pooled route only after its actual Pooler Service is qualified. |
| Status and wake | [ClusterDialer](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/session/cluster_dialer.go) first dials the backend. Connection refusal or DNS absence can trigger status lookup and reactivation, with bounded waits and coalesced status polling. | A useful later seam, not a drop-in match for the current creation-only regional protocol. |

The dialer's [protobuf contract](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/proto/clusters/v1/clusters.proto) uses only `DescribePostgresCluster({id})` and `UpdatePostgresCluster({id, update_configuration: {hibernate: false}})`. Description supplies configuration, status type, instance counts and per-instance primary/readiness information. Wake does not require implementing the protobuf service's other provisioning, credential, metrics or deletion methods.

## Runtime dependencies and ownership

The unchanged [gateway service](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/gateway.go) requires an in-cluster Kubernetes client, an IP-filter ConfigMap watcher, mounted TLS files and a cell-local clusters gRPC client. Keycloak, Xata projects/auth and a separate management database are not direct requirements of this native connection path. Observability exporters are configuration-dependent; the [observability configuration](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/internal/o11y/config.go) defaults tracing off.

Installing the actual [Xata clusters service](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/clusters/clusters.go) adds Branch/ClusterPool resource models and updates Branch CRs. It is not an adapter for existing PGCF-owned CNPG Clusters. Its [configuration](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/clusters/config.go) also assumes storage/snapshot and cloud-provider settings. Taking this management stack unchanged would conflict with the selected controller ownership and expand scope.

## Possible bounded adapter

The following is an integration proposal to evaluate, not an approved implementation or proven patch size:

1. Retain the TLS initiator, byte forwarding, draining lifecycle and metrics. Supply a PGCF resolver, backend dialer and access policy through narrow wiring changes rather than importing Xata's management stack.
2. Publish validated regional route entries after current CNPG/Pooler readback, identifying environment, region, immutable spec revision/hash and Cluster UID. Resolve only approved hostnames and actual direct/pooled Services. Maintain the last authorized regional configuration without a D1 request on every connection; policy expiry and revocation still require a contract.
3. Dial the backend with PostgreSQL TLS negotiation and CA/Service identity verification. PostgreSQL/CNPG remains the database authentication authority; route publication never exposes private role credentials.
4. Keep the initial pilot always-on and reject wake mutation. Later map only an authorized `hibernate: false` request into a coalesced regional lifecycle operation, with policy/budget authority and fenced reconciliation. Do not accept arbitrary Xata configuration updates through that adapter.

PGCF currently records `environment.create` through regional claims, lease renewal and fenced observations. It does not yet implement endpoint discovery, database credential issuance, wake, suspension or budget authority. Those contracts cannot be assumed to exist because the gateway can connect to a backend. The integration must preserve the generic environment model and leave consumer-specific adapters outside this repository.

## Concrete gaps in unchanged components

- **Backend encryption:** the native proxy sends PostgreSQL startup directly over the dialer's plain TCP connection. Client TLS termination does not establish verified gateway-to-PostgreSQL TLS. The backend dialer needs an explicit encrypted, verified path before claiming that property. [Proxy](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/session/proxy.go), [dialer](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/session/cluster_dialer.go)
- **Wake authorization:** backend dialing/reactivation precedes PostgreSQL credential verification. The unchanged path does not satisfy PLAN's authentication-before-costly-wake requirement; the always-on pilot avoids wake but does not resolve the later requirement.
- **IP-policy defaults:** absent branch rules allow access; ConfigMap deletion or a missing `ipfiltering.json` key clears rules. This policy must be reconciled with any promised fail-closed installation boundary. [Filter](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/ipfiltering/filter.go)
- **Source-IP trust:** the [listener](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/gateway_server.go) accepts PROXY headers from every source. Source-based policy therefore needs a restricted trusted-L4 ingress path or changed listener policy. This is a source-level integration gap; no deployed bypass or exploit was tested.
- **Cancellation and hostname routing:** TLS is required before CancelRequest handling, and routing uses SNI. Legacy plaintext cancellation and clients without the expected hostname cannot be advertised as compatible without a verified path. The built-in resolver validates an identifier but does not check an installation-owned DNS suffix.
- **Internal RPC trust:** the [gRPC client](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/internal/grpc/client.go) defaults to insecure transport. A retained adapter service needs an explicit regional authentication/network boundary; it is not a public management endpoint.
- **Deployment assumptions:** [chart defaults](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/charts/gateway/values.yaml) use AWS NLB annotations and `latest`; [deployment](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/charts/gateway/templates/deployment.yaml) references `otel-config` and Stakater Reloader for certificate changes. Contabo exposure, artifact pinning and certificate refresh need our own qualified configuration. Native-only execution must explicitly set `XATA_SQL_GW_HTTP_ENABLED=false`: its [runtime default](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/services/gateway/config.go) is true, while disabling the chart port alone does not set false.

These are reasons not to infer PGCF compatibility or isolation from unchanged code. They are not validated vulnerability findings or claims about a deployed Xata installation. Upstream itself [advises against unchanged public Postgres-as-a-Service use](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/README.md), stating that some adversarial multi-tenancy protections remain closed-source.

## Maintenance evidence and acceptance boundary

Recent gateway-path commits include [coalesced status lookups on September 21](https://github.com/xataio/xata/commit/91594f434e82b327db18ccff6abff3d743f9fe9a), [span links on September 22](https://github.com/xataio/xata/commit/95f7bc1a65d1aa08b43a98bd6583ad75f50b1269), and [reachability tracing on September 23](https://github.com/xataio/xata/commit/fe33ee28ffc481842ab1e28863d9f65f1c9c4ad4). This establishes recent public activity, not an update or security-response guarantee. On the review date, GitHub API [release](https://api.github.com/repos/xataio/xata/releases?per_page=3) and [tag](https://api.github.com/repos/xataio/xata/tags?per_page=3) listings were empty; this dated observation does not predict future releases.

The [contribution guide](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/CONTRIBUTING.md) describes an internal-monorepo mirror and copied contributions. The [module](https://github.com/xataio/xata/blob/98ced3cc9d5038c78c7f3a00ab7d22da847a4fdd/go.mod) requires Go 1.27.1 and pins Xata CNPG fork API dependencies. Any integration needs an owner, pinned source/artifacts, dependency/license review, tracked adapter changes and an update process. Build compatibility with PGCF's selected CNPG release is unverified.

Compared only with direct CNPG and CNPG PgBouncer, the gateway offers reusable routing, client TLS termination, draining and future wake seams, while adding policy, certificate, RPC and release obligations. It is not required to establish the generic always-on native pilot. No replacement of that baseline is decided here. Native clients, cancellation, direct/pooled semantics, credential invalidation, current-readiness observation, outage behavior, limits, wake authorization and tenant isolation still require bounded runtime acceptance before any corresponding guarantee.
