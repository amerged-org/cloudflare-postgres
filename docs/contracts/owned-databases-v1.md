# Owned PostgreSQL databases v1

Create a logical PostgreSQL database inside an existing ready, API-managed environment, owned by a currently applied restricted role from that same environment. This completes the ownership capability needed for application schema migrations; it does not provide a public endpoint, backup qualification, independent budget enforcement or role/grant delegation.

## Customer contract

The collection is `/v1/organizations/{organizationId}/projects/{projectId}/environments/{environmentId}/databases`. `POST` requires organization `projects:write`, `Idempotency-Key` and exactly `{name,ownerRoleId}`. The name is a lowercase SQL identifier of at most 63 characters. Reject `app`, `postgres`, `template0`, `template1`, names beginning `pg_`/`cnpg_`, and the actual protected bootstrap database. Callers select an already applied same-environment role, never a backend URL, arbitrary SQL, namespace, Cluster, privilege or password. The server binds immutable environment/spec/Cluster/owner-role identities and returns `202 {database,operation}` without credentials.

Exact intention replay recovers immutable metadata; changed payloads under the same key conflict. Logical database names are unique per environment. `GET /{databaseId}` uses organization read scope and reports the last accepted resource observation. `GET /{databaseId}/credentials` requires write scope and returns `{credential:{databaseId,ownerRoleId,credentialRevision,username,password,database,observedAt,credentialVerifiedAt}}` only while the database is applied and its same owner has a currently applied credential. It uses the existing encrypted role credential and keyring, not another password store. During owner rotation the disclosure waits; after rotation it returns the owner's latest applied password. `observedAt` refers to the database observation; `credentialVerifiedAt` refers to the currently applied role credential. Metadata/credentials are observed state, not a guarantee of continuous SQL reachability or immunity to trusted administrative drift.

## Durable authority and rotation

Use separate immutable database intention and operation rows. Create the intention in the same primary D1 batch that conditionally binds the applied owner role version, credential and accepted namespace/Cluster/role/Secret observations. An owner cannot rotate while any database creation operation for that role is queued or running. The rotation transaction and database-intention transaction enforce symmetric checks. Expired leases keep the owner lock: uncertain creation is reclaimed through the same task, never treated as no effect.

The regional lane is `/v1/regions/{regionId}/database-operations/{claim|operationId/renew|operationId/result}` with the existing executor claim/report scopes. Claims include only the exact bound current task, owner password and ordinary fenced lease. A revoked token, disabled region, changed environment/owner authority, expired/stale lease or mismatched result cannot publish success. Historical exact result replay returns immutable old metadata without changing newer state. Errors contain stable codes, never credentials or raw provider/SQL bodies.

## CNPG application and trusted writer boundary

CNPG's Database CRD may adopt an existing SQL database and alter its owner. Read the deterministic CR first. Resume an exact owned resource after a lost response; reject foreign ownership or divergent immutable specification. If no owned CR exists, require complete namespace Database-CR inventory with no competing manager and a fresh password-authenticated TLS catalog check proving the requested SQL name absent before creating anything. Existing SQL databases are conflicts, including when a former CR is missing. Never rename or delete an existing database to make creation pass.

D1 serializes supported platform creates and customer roles remain `NOCREATEDB`. The read/create interval is not atomic against an uncoordinated privileged administrator; administrators are trusted writers and must coordinate with the platform. This API does not claim an absolute non-adoption guarantee against arbitrary concurrent superuser SQL or another independent Database operator. Do not replace a missing upstream create-only primitive with an unsafe post-create ownership assertion.

The fixed Database specification uses `cluster.name: database`, the validated SQL name and owner, `ensure: present`, `template: template0`, `isTemplate: false`, `allowConnections: true` and `databaseReclaimPolicy: retain`. Customers cannot set `ensure: absent` or arbitrary CR fields. Retain protects CR deletion; it does not itself prevent a DROP request. No database deletion/alter-owner route ships in this slice.

Wait for exact owned CR identity/spec, applied status and current observed generation. Recheck namespace/Cluster/role/credential/Database identities and versions around a fresh TLS connection to the derived internal RW service and requested database. Verify expected user/database, writable primary, SQL owner OID, allowed connections, ordinary database and restricted role attributes. Prove migration capability with a generated schema/table round-trip inside `BEGIN`/`ROLLBACK`; create no persistent probe objects and never replay uncertain committed customer writes. Success reports the SQL OID and rollback-confirmed schema capability. A patch/CR Ready condition alone is insufficient.

## Bounded qualification

Three meaningful red-first top-level cases cover the customer create/disclose/owner-rotation lifecycle, uncertain regional creation with exact application/SQL proof, and refusal to adopt a pre-existing unmanaged SQL database. Existing role cases verify the shared authentication/credential helpers. Run only named affected tests during iteration and one final canonical gate after freezing the candidate. Real CNPG SQL creation/ownership/migration, networking, recovery and public access still need independent installation evidence.
