# PGCF security patch implementation plan

**Status** — Implemented locally on 2026-11-17. See ULTRA for qualification and production rollout evidence.

**Goal** — Ship the current supported Debian 13 node image with the PostgreSQL 18 security update to EU1 and US1, make the release of project SQL passwords auditable, and prevent project-scoped lookup errors from disclosing resource existence.

**Architecture** — P1 changes the signed Debian node release and its CI fixture. P2 adds a D1 record at the one public management path that returns SQL passwords and an operator read API. P3 restricts management lookups at the database query. Each patch can be reviewed and shipped independently.

**Stack and design references** — PostgreSQL 18, PGDG on Debian 13, pgvector, Rust node agent, Cloudflare Workers and D1, Hono and shared Zod contracts. See the [canonical delivery plan](cloudflare-convergence-and-serverless-plan.md), [maintenance procedure](../operations/recovery.md#node-maintenance-cycle) and [credential runbook](../operations/credentials.md). The plan follows the [Superpowers writing-plans method](https://github.com/obra/superpowers/blob/22f0b463e7a5e579904dd6211a520321035526f7/skills/writing-plans/SKILL.md).

## Execution constraints

- Work on P1 first. Prepare P2 and P3 independently of the node rollout. Use one reviewable commit or PR per patch and the existing CI workflow.
- Start each code fix with a failing regression. Use the actual image and real PostgreSQL for engine qualification. Only a real EU1 check on operator-owned fixtures counts as live acceptance.
- Keep access keys, SQL passwords, connection URIs and private evidence out of logs, diffs and test output. Any production write requires the owner's explicit, costed go. This plan uses the existing nodes. Present CI, storage and request costs, the maintenance impact and the rollback boundary before rollout.
- Record completed work, measured results and release identities in the canonical ULTRA plan. The checklist below describes proposed work.

## Review focus

| Failure mode | Check that decides acceptance |
| --- | --- |
| The new agent converges while the old PostgreSQL packages still serve | P1 requires completed OS maintenance, matching lock digest and a SQL version read from a newly started operator-owned database. |
| An existing C extension was built against the previous server headers | P1 checks the pgvector package build record and reads an existing vector table after the upgrade. |
| A D1 retry or a reused client request ID changes the number of recorded password releases | P2 requires one record per authorized response and a stable server-generated ID across internal write retries. |
| A role password rotates around a read, or a HEAD request follows the GET handler | P2 records the revision from the same row as the released ciphertext. HEAD preserves authorization and sends no password or disclosure event. |
| Project filtering hides expected history or removes fleet-wide read access | P3 retains deleted-database operation history and both administrator read scopes, with focused regression checks. |

## P2 · Record project SQL credential releases

**Files.** Create `apps/api/migrations/0101_credential_disclosures.sql` (next free number after the archive digest migrations) and `apps/api/src/domain/credential-disclosures.ts`. Integrate at [connectionUri](../../apps/api/src/domain/roles.ts), [audit route registration](../../apps/api/src/routes/audit-events.ts), [OpenAPI metadata](../../apps/api/src/openapi-metadata.ts) and the [shared management contract](../../packages/contracts/src/api.ts). Use the existing [credential response test](../../apps/api/test/domain/domain.test.ts), [audit error and pagination tests](../../apps/api/test/platform/admin-accountability.test.ts) and [OpenAPI tests](../../apps/api/test/openapi.test.ts).

**Interfaces.** Add `GET /v1/credential-disclosures` for `admin` and `admin_read`. Accept optional validated `key_id` and the usual `limit` and `cursor`. Return the existing list envelope, newest first by `(created_at, id)`. Define a strict `CredentialDisclosure` Zod row with `id` (server UUID), `key_id`, `project_id`, `database_id`, `role`, `role_created_at`, `password_revision` and `created_at`. Record the role's creation timestamp from the same row as its password revision so a recreated role with the same name can be identified. The event means the server authorized release of that credential. Whether the client received the response is unknowable.

- [x] **Red.** Extend the existing credential test to expect one disclosure for the authorized response. Add assertions for two independent GETs using the same client request ID (two records), a lost D1 acknowledgement followed by a retry (one record), and a terminal audit write failure (5xx with a generic body). Validate secret exclusion with boolean assertions that cannot print the secret on failure. Run the focused tests below. The current checkout lacks the disclosure record and route.
- [x] **Persist only the required metadata.** Create the additive table using a UUID primary key, existing ID constraints and positive password revision. Index `(created_at, id)` and `(key_id, created_at, id)`. Preserve records through key revocation and role/DB deletion. Apply the existing 90-day cutoff to reads and reuse the existing cleanup-on-write convention, keeping the minute cron budget intact.
- [x] **Guard the response.** In the authorized integrator GET, validate the existing response shape, prepare the password-bearing result and await its disclosure insert before returning it. Source the revision, DB and role from the same row used for decryption. Generate one UUID per incoming GET. Use the [existing bounded retry and unique-ID pattern](../../apps/api/src/middleware/audit.ts) for ambiguous D1 acknowledgements. A terminal write error must return a generic response without a URI. Authorized HEAD requests and passwordless admin responses keep their current status and headers. Test that HEAD skips decryption and that these responses and refused requests produce zero disclosure records.
- [x] **Expose the record.** Add the filtered, paginated operator read route, register the metadata and update the management API contract from `1.7.0` to `1.8.0` for this baseline. Keep the existing strict admin audit response compatible. Test admin and read-only admin access, integrator refusal, key filtering across a page boundary and exclusion of expired records. Confirm the stored revision matches the returned credential when a role changes concurrently.
- [ ] **Green and review.** Run `pnpm --filter @pgcf/api exec vitest run test/domain/domain.test.ts test/platform/admin-accountability.test.ts test/openapi.test.ts` and the existing CI. Document in the [credential runbook](../operations/credentials.md) how to query by compromised key, revoke the API key and separately rotate affected SQL roles. Reads from before rollout have no per-role record. Review and commit P2 independently.
- [ ] **Deploy and accept.** After the costed production go, apply the additive D1 migration before updating the Worker. Using operator-owned EU1 fixtures, verify one credential read yields one matching event and the admin and HEAD checks yield none. Keep the additive table and existing records across a Worker rollback. Returning to a Worker predating P2 reopens the audit gap, so document any such interval.
