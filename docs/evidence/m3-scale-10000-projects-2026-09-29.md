# Ten-thousand-project feasibility checkpoint — 2026-09-29

Ten thousand logical projects are a product target, not a verified current
capacity. Project records may exist without a PostgreSQL environment. Ten
thousand provisioned environments are a separate compute, storage, network,
backup and operating-cost question.

## Recovery-shape and isolated D1 probes

An offline in-memory SQLite run used the committed 15-migration schema and
inserted 10,000 additional project rows under the existing fixture organization.
The resulting 10,001 project rows and 10,024 total application rows were read by
the existing single-query control snapshot. The generated SQL was 98,397 bytes;
the returned `snapshot_json` string was **2,576,706 bytes**. The snapshot body
was 2,576,347 bytes. Local capture took 94 ms, and the whole local exercise took
214 ms. The private fixture and report contain synthetic data only.

That initial result was **not a D1 success**. The former recovery adapter capped
one result string at 2,000,000 bytes, matching [Cloudflare's D1 limit of 2,000,000 bytes
per string or row](https://developers.cloudflare.com/d1/platform/limits/).
The one-row snapshot therefore exceeds that limit even though its 8 MiB
envelope and 100,000-row count limits are not reached. The 100,000-byte SQL
statement limit is a separate schema-size constraint; shortening column
references cannot solve the result-size problem. The published alias change
reduced the 15-migration query to 84,958 bytes without changing its result;
after resize migration `0016`, the one-read query measures 93,428 bytes.

A follow-up, still offline and synthetic, applied the current 16 migrations
and measured a row-oriented shape over 10,000 project records. Across the
schema, 47 application tables and sequences it returned 10,019 rows and
2,560,161 bytes of cell content; the largest cell was 58,981 bytes. The
49 separate SELECTs used for this shape measurement do **not** form a proven
consistent remote backup. The implemented recovery reader instead uses one
read-only SELECT with deterministic ordering, row counts for every table and
the sequence, and a terminal marker. It must reject missing, duplicate,
reordered or truncated rows before sealing an archive. That 16-migration query
was 89,572 bytes as a flat `UNION ALL`, but live D1 rejected its 97 direct
terms with `too many terms in compound SELECT` (HTTP 400, code 7500). Nested
pairs keep one ordered SELECT and measure **92,644 bytes**, below the 99,000-byte
guard and D1's 100,000-byte limit. A constrained local SQLite run with a
three-term compound limit failed first on the flat query and passed after the
change.

Two new top-level tests failed before implementation and now pass. A local
single-read fixture with 10,001 projects produces the same v1 snapshot digest
as the historical one-row format, seals an encrypted archive and independently
restores all 10,001 project rows with foreign-key and integrity checks. A
second case removes a data row and verifies capture fails rather than
publishing a shorter archive. The compound-limit case adds one top-level
regression; the targeted recovery
file now passes all five cases.

The balanced statement succeeded against the existing Dev D1 as a read-only
query. A separate EU-jurisdiction D1 was created with the 16 pinned migrations
and **10,000 synthetic projects**; no synthetic project was added to the Dev
control database. Its single rowset query returned **10,067 result rows** in a
**2,685,057-byte** HTTP response, with **126.0 ms** reported SQL duration. The
same captured rows rebuilt a private SQLite database with **47 tables, 10,017
application rows and all 10,000 projects**; `integrity_check` was `ok` and
`foreign_key_check` returned no errors. The temporary D1 was deleted, and a
subsequent provider GET returned 404. A prior synthetic run used a differently
formatted migration-table DDL and correctly failed the exact-schema check;
the final run used the pinned DDL. Raw rowsets and account credentials remain
in ignored owner-only local files.

This proves this one synthetic metadata snapshot and exact offline rebuild
through the D1 REST API. It does **not** prove concurrent-write consistency,
customer-data/keyring custody on live D1, the Wrangler operator path (its
current Dev authorization still returns `7403`), or 10,000-project request load.

The public API already uses indexed, bounded project pagination. That proves an
enumeration contract, not 10,000-project write throughput or disaster recovery.
[D1 documents](https://developers.cloudflare.com/d1/platform/limits/) a 10 GB
maximum database on Workers Paid and single-threaded query processing per D1
database. Read replicas can increase read throughput only when the
[Sessions API](https://developers.cloudflare.com/d1/best-practices/read-replication/)
is used; they do not make one primary's writes parallel. The account plan and
representative request rate are not established by this recovery probe.

## Design and acceptance work

Before advertising general 10,000-project support, prove capture with
concurrent writers, operator-held credential custody and operation history,
then measure representative API traffic and independently restore it. A single
SQLite SELECT provides one read view; consecutive normal reads do not provide
that guarantee while writers are active. The result must fit the independent
per-cell, SQL-statement, query-duration, CLI-output, row-count and encrypted
archive bounds. The current archive remains capped at 8 MiB, so larger
workloads need a separately designed, chunked archive with bounded parts,
source identity, ordering and digest. Publish its manifest only after all
parts are retained and independently restored. [D1 export](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/)
is not assumed to be a transparent online snapshot because it can block the
database during export.

If one database cannot meet the measured workload, partition control state into
bounded shards. An organization directory, project routing, token
authorization/revocation, idempotency, budget reservations and recovery need
explicit versioned ownership. Keep each project's environments, roles,
operations and usage history in an atomic project shard. An organization with
many hot projects may need project-level partitioning; organization-only sharding
does not resolve that case. No D1 transaction spans shards. Global budgets must
use bounded, reconcilable grants so cross-shard updates cannot authorize
unlimited consumption or double-charge usage.

The live acceptance gate is one representative 10,000-project workload in an
isolated installation: report write/read rates, p95/p99 latency, D1 queue or
overload errors, storage growth, authentication and budget contention, and a
full independently verified restore. Choose target service objectives before
marking it passed. Separately model environment density, persistent volume,
replica and spare-capacity costs. The current two-VPS lab, with one Talos
database node and one builder, is not evidence for 10,000 PostgreSQL
environments. No synthetic projects were created in the live Dev control DB.
