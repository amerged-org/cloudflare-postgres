# M1 infrastructure checkpoint — 2026-09-28

Status: **partial live evidence**. A single-node Talos/Kubernetes/PostgreSQL lab is running, but no R2 backup or restore has been proven. This record contains no credentials, account or instance IDs, network addresses, host keys, or customer material.

## Verified on the disposable Contabo lab VPS

- The account has two purchased VPS in one data center. One is the Talos lab; the second remains an Ubuntu image builder. This is not a high-availability or independent-failure-domain topology. A pre-install Ubuntu snapshot remains available until the provider's reported 2026-10-27 expiry; it is a lab rollback point, not a database backup.
- Contabo custom-image storage was unavailable. We used Contabo's RAM-based rescue system to write an official Talos v1.14.1 NoCloud disk image to the one verified lab disk. The Image Factory schematic contains a nonsecret static-network kernel argument, no machine configuration, and no CIDATA partition. The downloaded image, decompression, partition table, and written partition data were checked before boot. The full machine configuration stayed in ignored, owner-readable local files and was applied through the restricted Talos maintenance API. The resulting authenticated API and node identity survived reboot.
- The provider firewall is attached only to the lab VPS. It permits the operator IPv4 address to reach the limited administrative ports and drops other ingress. The second VPS could not reach the checked lab ports over IPv4 or IPv6. This is a lab access rule, not a complete production network policy.
- Talos v1.14.1 runs Kubernetes v1.36.3 with Cilium v1.20.2. Flannel and kube-proxy are disabled. The one node, Cilium agent and operator, CoreDNS, a disposable Pod DNS lookup, and `talosctl health` passed. The DNS test Pod was removed.
- Talos created a 40 GiB EPHEMERAL volume and a separate 96 GiB raw partition. Its declarative LVM volume group `pgcf` was writable with one physical volume, and both the volume layout and group survived a node reboot. The group is independent of Talos's EPHEMERAL filesystem.
- OpenEBS 4.6.1 was installed with only LocalPV LVM 1.10.1 enabled. The dedicated `openebs` system namespace allows its privileged CSI node driver; customer namespaces were not changed. StorageClass `pgcf-lvm` selects only the `pgcf` group, uses thick provisioning and `WaitForFirstConsumer`, and retains ordinary volumes on claim deletion.
- A disposable 64 MiB claim bound successfully. Its mounted filesystem reported bounded capacity; a write beyond that capacity failed with no space left. A marker remained readable from the same claim after a Talos reboot. We then removed both test Pods, changed only that test PV's reclaim policy for cleanup, removed the claim, and read back zero logical volumes and all group space free.
- cert-manager v1.21.2, the CloudNativePG v1.30.1 operator, and Barman Cloud plugin v0.15.0 have healthy deployments. Plugin certificates and the database/ObjectStore CRDs are ready.
- A manually created, one-instance CloudNativePG PostgreSQL 18.4 Cluster is ready on a bound 5 GiB `pgcf-lvm` PVC. A transaction through an ordinary PostgreSQL client Pod used the read/write Service, application credentials, and verified TLS against the cluster CA. Both that SQL marker and an in-Pod marker remained readable after a Talos node reboot, with the same PV bound. During restart, the Cluster status briefly preceded the actual Pod state; CloudNativePG deleted the completed Pod and recreated a Running/Ready primary. Readiness evidence includes the Pod and SQL readback, not only the Cluster condition. The Barman plugin is installed but not yet configured on this Cluster; no backup Secret has been created.

The Cloudflare development D1, R2 bucket, and control Worker are recorded separately in the [M3 control API checkpoint](m3-control-api-dev-2026-09-27.md). The R2 bucket has not yet received a PostgreSQL backup.

## Gates still open

1. Issue a bucket-scoped R2 S3 credential, configure the existing CloudNativePG Cluster for Barman, and prove WAL continuity, a physical base backup, full restore, and an independent point-in-time restore. A Cloudflare API token is not an R2 S3 access key.
2. Verify backup retention and safe deletion without breaking a recovery chain; measure RPO, RTO, storage growth, and failure behavior.
3. Test node replacement, staged Talos/Kubernetes/PostgreSQL updates, and restore onto fresh infrastructure. One node cannot prove failover. The two purchased VPS in one data center do not prove independent failure domains.
4. Replace manual lab installs with a repeatable owner-controlled release process, and prove regional operation during management and object-store outages. The regional controller, gateway, tenant isolation runtime, and usage/budget enforcement are not implemented.
