# CNPG native session pooling

These opt-in examples configure a single internal read/write PgBouncer through CloudNativePG 1.30.1. They are not included in Flux or automatic environment creation. Replace the example namespace, Cluster and Pooler names, qualify the result, then integrate it with the installation's ownership and network policies. No public Service or customer endpoint is created.

Use [frontend-certificates.example.yaml](frontend-certificates.example.yaml) to create an independent cert-manager CA and Pooler server certificate. Wait for both Certificates and both Issuers to become Ready before creating [session-pooler.example.yaml](session-pooler.example.yaml). Distribute only the frontend CA certificate to clients. Its private key and the leaf private key stay in Kubernetes Secrets; clients receive neither. Verify the actual issued SANs and expiry. CA rollover and application trust updates require their own procedure; automatic leaf renewal does not establish seamless root rollover.

Clients must use the exact Pooler DNS name and verify the frontend CA and hostname. `client_tls_sslmode: require` refuses unencrypted PostgreSQL clients. PgBouncer uses `server_tls_sslmode: verify-full` to verify PostgreSQL's CA and its generated backend hostname, the short `<cluster>-rw` Service name. Confirm that name appears in the PostgreSQL server certificate before deployment. The independent frontend leaf avoids changing the Cluster server certificate or adding Pooler DNS names to it.

Only `clientTLSSecret` is set. CNPG 1.30.1 still supplies its automatic `cnpg_pooler_pgbouncer` authentication integration and client certificate for the internal authentication query. Do not set `authQuery`, `authQuerySecret` or `serverTLSSecret` unless deliberately replacing that integration. Ordinary roles continue to authenticate with their own passwords; the client-facing certificate does not grant SQL privileges.

The pinned PgBouncer 1.25.2 image index is `sha256:b15c428057d1ffbc19fb70496911a5f1a47066dcc1315bf794f4e85ade29e2e5`; its verified Linux amd64 manifest is `sha256:e5e357435dd97c43fc46099f32b2ad3a3d1e830d409bafbde8c0eba8c9541733`. Preserve the upstream ISC license. CPU/memory reservations, 50 client slots, five backend slots per pool and ten backend connections per database/user are qualification values, not universal product limits or a fleet-wide connection cap. Each database/user pool and each Pooler replica adds ownership and capacity considerations. Direct connections also consume PostgreSQL capacity.

Session pooling retains a backend while a client is connected, supporting interactive transactions and session state. Idle application sessions can occupy all backend slots. This single-instance example uses Recreate to avoid an overlapping rollout replica; updates can disconnect clients. The direct RW path remains necessary for documented maintenance and migrations; grant it only within the installation's access boundary. Transaction pooling, multi-replica cancel peering, failover, password expiry, frontend-key renewal and load limits require separate evidence. CNPG ignores the startup `options` parameter by default, so session settings must be applied explicitly after connecting when needed.

Qualify a current-generation owned Deployment, exact pinned image, ready Pod, Service endpoints and issued certificates. Then use fresh password-authenticated connections to verify TLS, SQL role/database identity, writable primary, transaction rollback and session-state behavior. Demonstrate plaintext refusal and bounded cancellation/reconnect behavior. A Pooler `active` status or TCP readiness probe alone is insufficient. Preserve source Cluster/Pod/PV identities and existing SQL markers across installation.

Network and accounting integration remain installation work: permit only the intended gateway/client identities to Pooler TCP5432, Pooler-to-Cluster TCP5432 and required DNS/API paths. Account for its Pod in namespace quotas and regional usage without attributing shared infrastructure arbitrarily. The examples provide no tenant-isolation guarantee, sleep/wake routing, API endpoint publication or budget enforcement.
